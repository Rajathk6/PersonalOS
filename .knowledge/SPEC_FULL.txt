PersonalOS
Complete Architecture, Product, Engineering, and Evolution Specification for OpenCode
Version: Comprehensive design baseline • Purpose: implementation guidance and long-term architectural north star
This document consolidates the complete PersonalOS discussion: product intent, architecture, extensibility, model routing, multi-node execution, offline/power recovery, permissions, personal-data verticals, rejected alternatives, implementation phases, and long-term evolution.
1. Purpose
Build PersonalOS as a serious, extensible, local-first personal AI operating system/platform. It is not a toy chatbot, a single autonomous agent, or a collection of unrelated scripts.
Understand high-level goals from natural language.
Research and reason about goals.
Plan and execute multi-step work.
Remember relevant information across time.
Schedule and follow up on work.
Interact with external tools and services.
Manage structured personal information.
Monitor changing external information.
Coordinate multiple AI/model providers.
Distribute work across multiple computers.
Recover from power/network interruptions.
Acquire new capabilities without rewriting the core.
Discover and integrate new models/providers.
Expose the system through phone, browser, CLI, voice, or other clients.
The system must be designed so that future capabilities are not limited by what is known today.
2. Fundamental Product Concept
PersonalOS is an operating environment for a person's goals, information, tasks, AI agents, tools, memory, and computing resources.
It is not initially a replacement for Linux, Windows, or another kernel-level operating system. The underlying OS continues to manage CPU, memory, storage, networking, drivers, and processes.
Physical Hardware      ↓Linux / Operating System      ↓PersonalOS Runtime      ↓PersonalOS Core      ↓Capabilities / Agents / Tools / Memory / Tasks      ↓User Interfaces
Eventually PersonalOS may be packaged as a Linux-based appliance/distribution for a Raspberry Pi, mini PC, or dedicated home server. Do not begin by building a custom OS kernel or Linux distribution.
3. Core Product Philosophy
PersonalOS should behave as though it has persistent identity, memory, tasks, goals, knowledge, workflows, tools, models, and computational workers.
The intended interaction is high-level goal setting. For example: “I want to become job-ready for backend development.” The system should eventually infer the research, planning, scheduling, teaching, evaluation, adaptation, and memory work needed to pursue that objective.
4. Do Not Build a Single Super-Agent
User ↓Intent / Request Layer ↓Orchestrator ↓Planning ↓Capabilities / Agents / Tools ↓Verification ↓Persistent State + Memory ↓Scheduler / Follow-up
Planner
Researcher
Executor
Coder
Analyst
Critic
Verifier
Memory Agent
Coordinator
These are logical roles, not necessarily separate running models. Initially several roles can use the same local model. Do not start multiple heavyweight LLM processes merely to create a multi-agent appearance.
Why the single super-agent approach is rejected
Prompts become enormous.
Capabilities become tightly coupled.
Testing becomes difficult.
Permissions become difficult to reason about.
Failures become difficult to isolate.
Adding a new vertical requires modifying core reasoning.
Model replacement becomes difficult.
Task recovery becomes difficult.
Long-running workflows become fragile.
Decision: use a central orchestrator with modular capabilities and logical agent roles.
5. Hardware and Real-World Constraints
Initial machine: Intel i7 11th-generation laptop.
12 GB RAM.
Intel integrated Iris graphics.
1 TB SSD.
Linux.
No NVIDIA GPU.
Initial software budget: ₹0.
Airtel dongle with roughly 1 Mbps practical bandwidth.
Electricity can unexpectedly go out.
Local quantized LLMs are the primary initial AI path. Small 3B models are easiest; 7B/8B models are practical depending on quantization; 14B may be possible but substantially slower; very large models are not appropriate for this hardware.
6. Internet and Power Are Environmental Conditions
Do not assume continuous internet, continuous electricity, continuous laptop availability, or continuous network availability.
Power loss and internet loss are normal operational conditions, not exceptional application failures. Important state must be persisted so the system can recover.
7. Power-Loss Recovery
Machine boots ↓PersonalOS starts ↓Database opens ↓Persistent state recovered ↓Scheduler recovers ↓Queue recovers ↓Workers register ↓Pending tasks inspected ↓Catch-up policy evaluated ↓Appropriate work resumes
A task must never exist only inside an LLM context. Important task state, checkpoints, outputs, retries, and dependencies must be persisted.
8. Catch-Up Semantics
Do not blindly replay every missed scheduled run.
Daily government-job monitor08:00 every daySystem is offline for 3 days.On recovery:    last successful checkpoint = Oct 4    current date = Oct 8Preferred behavior:    perform one catch-up scan covering changes since Oct 4    deduplicate results    update checkpoint
Recurring tasks need a semantic catch-up policy, last successful checkpoint, external-state tracking, idempotency, and deduplication.
9. Scheduler → Task → Queue → Worker
The scheduler must not directly invoke Ollama.
Scheduler   ↓Task   ↓Queue   ↓Worker   ↓Model Provider / Tools
This separation is required for future Raspberry Pi + laptop + desktop distribution.
10. Initial vs Future Deployment
Initial:Laptop├── API├── PersonalOS Core├── PostgreSQL├── Scheduler├── Queue├── Worker├── Memory└── OllamaFuture:Raspberry Pi / Home Server├── API├── Database├── Scheduler├── Queue├── Memory├── Notifications└── Lightweight WorkersLaptop└── Heavy Worker    └── Ollama
The initial deployment may be a modular monolith on one laptop, but the code must not assume that all components will permanently live on one machine.
11. Raspberry Pi as Coordinator
Eventually the Raspberry Pi can act as the always-on PersonalOS coordinator and source of truth for API, database, scheduler, task queue, memory, capability registry, model registry, worker registry, notifications, and persistent state.
It does not need to perform every heavy AI task.
12. Laptop as an On-Demand Worker
Laptop starts ↓PersonalOS Worker starts ↓Worker registers and reports capabilities ↓Coordinator assigns suitable pending tasks ↓Laptop executes ↓Result is persisted centrally ↓Laptop can become idle or shut down
The laptop should be treated as a replaceable worker, not the permanent identity of PersonalOS.
13. Capability-Aware Workers
Raspberry Pi:  database  scheduler  notifications  web requests  lightweight computeLaptop:  local_llm  coding  document_analysis  cpu_computeFuture GPU desktop:  large_llm  image_generation  video_processing  heavy_compute
The orchestrator should ask which available worker can perform a task rather than hard-coding a specific machine.
14. Wake-on-LAN
Eventually the Pi may wake the laptop using Wake-on-LAN if the hardware/firmware supports it. The sequence can be: pending heavy task → no capable worker → Wake-on-LAN → laptop boots → worker registers → task executes → result returns → graceful shutdown.
Wake-on-LAN is optional and hardware-dependent. Do not make it a foundational assumption. Never use forced power removal as a normal shutdown mechanism.
15. Phone Architecture
The phone should be a thin client of PersonalOS, not a second independent intelligence stack.
Phone ↓PersonalOS API ↓Central PersonalOS
The phone can send natural-language requests, receive notifications, display task status, and handle approval prompts.
16. PersonalOS Is a Platform, Not a Fixed Feature List
The concept evolved from a customized agent to an AI OS, phone interaction, notifications, finance, expense tracking, stocks, government-job monitoring, and future unknown verticals. This proves the core cannot be built around a fixed list of features.
The architecture must support future domains without rewriting the Core.
17. Vertical / Capability Architecture
PersonalOS Core      ↓Capability Registry      ↓FinanceStocksGovernment JobsProjectsTravelReadingFuture Capability
A capability should declare its name, version, capabilities/actions, entities, workflows, tools, permissions, storage/migrations, UI where applicable, automations, and compatibility requirements.
18. Example Finance Capability
Finance CapabilityActions:  record_expense  record_income  calculate_net_worth  calculate_budget  track_loan  track_asset  track_investmentEntities:  account  transaction  income  expense  loan  asset  investment  budget  subscription

19. Future Capability Example
A future request such as “create a motorcycle vertical for fuel, maintenance, service history, insurance renewal, and maintenance recommendations” should be implementable as an installable capability rather than a rewrite of orchestrator.ts, scheduler.ts, memory.ts, or model-router.ts.
20. Capability Builder — Long-Term Goal
Eventually the user should be able to describe a new domain in natural language and have PersonalOS propose a capability design.
Requirement ↓Capability design ↓Schema/workflow generation ↓Validation ↓Security review ↓User approval ↓Installation ↓Registration
Do not implement the full Capability Builder in the first phase. Build the extension mechanism first.
21. Model Architecture
Model Registry      ↓Model Provider Abstraction      ↓Model Router      ↓Selected Model
Provider examples include Ollama, llama.cpp, OpenRouter, and future providers.
interface ModelProvider {  generate(request: ModelRequest): Promise<ModelResponse>;}
Model metadata should include model ID, provider, context length, modalities, tool calling, structured output, reasoning/coding suitability, latency, cost, availability, local/cloud status, and hardware requirements.
22. New Model Discovery
Provider ↓New model discovered ↓Inspect metadata ↓Compatibility check ↓Pricing/cost check ↓Tool support check ↓Benchmark where appropriate ↓Compare against existing models ↓Recommend adoption
Do not blindly replace a working model simply because a new model appears.

24. Model Policy / Content Freedom
Model choice should remain user-controlled and the application should not impose arbitrary content restrictions merely because a request falls outside anticipated product categories. Local models should be first-class providers.
However, content-policy freedom and operational authority are separate. A permissive model must not automatically gain unrestricted authority over the host system.

36. Queue
Use a persistent queue abstraction. Do not make Redis mandatory on day one.
A PostgreSQL-backed queue is acceptable initially. Redis/BullMQ may be introduced when actual throughput or distributed-worker requirements justify it.
37. PostgreSQL vs SQLite
Preferred architecture: PostgreSQL, because the system has structured personal data, concurrent workers, relational integrity, robust transactions, future multi-node deployment, and possible pgvector usage.
SQLite may be useful for an extremely simple prototype, but it must not force single-device assumptions. If used temporarily, isolate database access behind repositories/interfaces.

48. Authentication and Identity

49. Notifications
Notifications should be a provider abstraction.
Phone push
Web push
Desktop notification
Email
Messaging services
The scheduler produces notification events; notification providers decide delivery.
50. Documents
Documents should eventually be first-class data: uploaded, downloaded, generated, analyzed, summarized, associated with tasks/capabilities, and indexed. Provenance should be tracked.
51. Local-First Principle
Whenever practical, prefer local computation and storage. Do not make this ideological: local, cloud, or hybrid execution should be selectable based on privacy, quality, cost, and availability.
52. Network-Aware Operation
With approximately 1 Mbps connectivity, cache results, avoid repeated requests, deduplicate downloads, support resumable downloads where practical, avoid unnecessary model downloads, and keep heavy reasoning local.
Network-dependent work should be able to enter WAITING_FOR_NETWORK and resume later.
53. Internet Is a Data Layer, Not the Whole Brain
When the internet is unavailable, local memory, finance, tasks, documents, planning, local models, structured data, and scheduling should continue working. Network-dependent operations wait and resume.
54. Error Handling
ToolResult {  success: false,  error_code: NETWORK_TIMEOUT,  retryable: true,  message: "...",  metadata: {}}
Failures must become structured results rather than corrupting task state.
55. Idempotency
Important operations should be idempotent where practical. This prevents duplicate expenses after power loss, duplicate job alerts, and repeated side effects after retry.
56. Auditability
For consequential actions record who/what requested it, which agent proposed it, which policy allowed it, which worker executed it, which tool executed it, when it happened, and the result.
57. Human-in-the-Loop
Automate thinking and coordination aggressively, but preserve explicit approval for consequential actions such as financial transactions, destructive file operations, external communications, account/security changes, purchases, and high-impact system changes.

66. Externalized Configuration
Do not hard-code model names, API URLs, schedules, notification providers, worker addresses, permission rules, or capability settings. Use configuration and persistent registries.
67. Versioning
Capabilities, providers, and the Core should be versionable where practical. Compatibility should be checked before updates.
PersonalOS Core 0.5Finance Capability 1.2Government Jobs Capability 0.7Ollama Provider 1.1
68. Updates
Updates must preserve user data.
Backup ↓Migration ↓Update ↓Health check ↓Rollback if necessary
Database migrations must be explicit.
69. Security Principle
The model is not the security boundary. Authentication, authorization, permission evaluation, tool sandboxing, filesystem permissions, database permissions, worker authentication, and audit logs form the security boundary.
70. Shell Execution
Raw unrestricted shell access should not be the default. Commands should be proposed, risk-classified, evaluated by permissions, executed in an appropriately restricted environment, and audited.
71. Capability Security
Capabilities should receive only the tools they need.
Finance capability  database.finance.read  database.finance.write  notification.send
It should not automatically receive shell execution, arbitrary filesystem deletion, or financial transfer privileges.
72. Integrations
External integrations such as Gmail, calendar, GitHub, messaging, market data, cloud storage, government sites, RSS, APIs, smart-home systems, and others should be adapters/connectors. Provider-specific logic should not be scattered throughout the Core.
73. Data Ownership
The user's data is the primary asset. Important data should be exportable, backed up, inspectable, migratable, and not trapped inside an LLM provider. Models should be replaceable without losing memory or structured data.
74. Model Replacement Principle
Replacing one model with another must not require rewriting finance, scheduler, memory, tasks, capabilities, or UI. A model is a replaceable compute dependency.
75. Capability Replacement Principle
Capabilities should also be independently replaceable. A future Finance v2 should migrate existing accounts, transactions, loans, and assets rather than destroying state.
76. Core Stability Principle
Stable Core   │   ├── Registry   ├── Contracts   └── Persistent State          │          ├── Rapidly evolving Capabilities          ├── Rapidly evolving Models          ├── Rapidly evolving Tools          └── Replaceable Workers
The Core should change relatively slowly. Capabilities, models, tools, and workers should be able to evolve rapidly.
77. User Experience Goal
The system should feel simple even when its internals are sophisticated.
“Add ₹235 for the chicken tikka I had at 2:30.”
“Find new government engineering jobs and tell me if anything is worth applying for.”
“Remind me at 4 that I need to leave at 6.”
“Why did my portfolio fall today?”
“I want to start preparing for GATE.”
“Create a new vertical for my reading habit.”
The complexity should remain behind the PersonalOS interface.
78. Long-Term Autonomous Objective
High-level objective ↓Understand objective ↓Inspect user state/memory ↓Assess current situation ↓Research requirements ↓Build personalized roadmap ↓Create tasks ↓Schedule work ↓Execute ↓Evaluate ↓Adapt ↓Remember ↓Notify/follow up ↓Measure outcome
This is the direction, not an instruction to implement the entire loop immediately.
79. Rules for Future Ideas
New feature
Ask: Is this a Core primitive or a Capability? Most personal-domain functionality should be a Capability.
New model
Ask: Can it be represented through the existing ModelProvider and Model Registry interfaces? If yes, register it rather than changing the architecture.
New tool/service
Ask: Can it be represented as a Tool or Integration? Prefer an adapter over a special case in the orchestrator.
New hardware
Register a Worker, advertise capabilities, authenticate, and receive tasks. Do not hard-code machine identity into workflows.

81. First Principle
Do not build today's PersonalOS in a way that makes tomorrow's PersonalOS impossible.
At the same time, do not build tomorrow's infrastructure before today's requirements need it.
The solution is simple implementation + strong boundaries + stable interfaces + persistent state + extensible registries + capability architecture + worker abstraction, not premature distributed complexity.

83. Definition of Success
Requirement
Success condition
Extensibility
A new vertical can be added without rewriting Core.
Model independence
A new model/provider can be added without rewriting capabilities.
Hardware independence
A new worker can join without rewriting workflows.
Recovery
Power/network loss does not destroy persistent work.
Offline capability
Local functionality remains useful without internet.
Distributed capability
Pi can coordinate while laptop performs heavy work.
Security
Models cannot bypass permission boundaries.
User control
Consequential actions require explicit approval where configured.
Persistence
Important information survives restarts.
Natural interaction
User can express goals instead of technical prompts.
Cost
No mandatory paid API requirement.
Evolution
The system can gain capabilities for years without becoming a rewrite.
84. Final Instruction to OpenCode
Treat this document as the architectural north star, not as an instruction to implement everything immediately.
Inspect the current repository before changing anything.
Understand the existing implementation before modifying it.
Identify the smallest correct architectural change.
Preserve clean boundaries.
Persist important state.
Test failure and recovery behavior.
Avoid unnecessary infrastructure.
Document important decisions.
Keep Core generic.
Implement domain-specific functionality as capabilities.
Keep models behind providers.
Keep external actions behind tools and permissions.
Keep execution behind workers.
Keep scheduling separate from execution.
Design for eventual Raspberry Pi + laptop + phone operation.
Do not prematurely build distributed infrastructure.
Never sacrifice future extensibility merely to make the first prototype slightly faster to write.
The ultimate objective is not to build a chatbot with many features. It is to build a persistent, extensible PersonalOS platform whose capabilities can continuously evolve as the user's needs evolve while the underlying Core remains stable.
Target end-state: PersonalOS owns the persistent personal state, memory, tasks, goals, capabilities, workflows, and model/tool registry; available machines contribute compute as replaceable workers; new verticals are installable capabilities; new models/providers can be discovered and evaluated; power and network interruptions are recoverable; and consequential external actions remain behind an independent permission layer.
