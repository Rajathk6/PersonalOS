# ADR-006 — Capability Registry

Status: Accepted
Date: 2026-10-08

## Context
Core must stay generic and stable; domain logic lives in Capabilities (NORTH_STAR §3). First verticals are finance, jobs monitor, stocks; rule is new domain = new capability, never orchestrator rewrite. Extension mechanism precedes Capability Builder (Phase 11).

## Decision
Capabilities install via manifest (name/version/actions/entities/workflows/tools/permissions/storage-migrations/UI/automations/compat) with lifecycle DISCOVERED→VALIDATING→INSTALLED→ENABLED→DISABLED→UPDATED/REMOVED. Core exposes registry + events; capabilities subscribe without cross-domain hard-coding.

## Alternatives considered + why rejected
- Hard-coded verticals in Core: rejected — every new domain rewrites orchestrator; kills years-of-evolution goal.
- Unmanaged plugin folders: rejected — no version/compat/migration story; unsafe enable/disable.
- Build NL Capability Builder now: rejected — premature; need manual registry proven in Phase 7 first.

## Consequences
- Finance/jobs/stocks ship AS capabilities in Phase 7, proving the boundary.
- Migrations and permissions are per-capability, auditable and reversible.
- Phase 0 must do differently: define `Capability` manifest + registry interfaces (in-memory ok) now, keep Core free of finance/job terms, defer Builder.
