# ADR-004 — Task Queue Abstraction over PG

Status: Accepted
Date: 2026-10-08

## Context
Scheduler → Task → Queue → Worker must survive DB/queue restart and power loss (NORTH_STAR §4–5, failure simulations). ₹0 budget and single laptop rule out mandatory infra. Queue must support concurrent workers safely.

## Decision
Queue is an abstraction backed by a PG table, polled with `SELECT ... FOR UPDATE SKIP LOCKED` plus lease (owner + expiry) and heartbeat. Redis/BullMQ allowed only when measured throughput/lease pain justifies it via new ADR.

## Alternatives considered + why rejected
- Redis/BullMQ day one: rejected — second moving part, RAM persistence risk, unjustified at one-user scale.
- In-memory queue: rejected — process kill loses tasks; fails restart-recovery test.
- Direct function calls (no queue): rejected — no persistence, no retry, no multi-worker future.

## Consequences
- Power-loss recovery = rows, not RAM; duplicate-delivery handled by idempotency (see ADR-010).
- Single PG Compose service covers DB + queue + registries.
- Phase 0 must do differently: design `queue_jobs` with state/lease/attempts, implement poll→lease→execute→persist loop, test kill + `docker restart db` in Bundle 0C.
