# ADR-010 — Semantic Catch-Up

Status: Accepted
Date: 2026-10-08

## Context
Boot sequence is DB open → recover → inspect pending → catch-up policy → resume (NORTH_STAR §5). Recurring/monitoring tasks keep last-successful-checkpoint; 3-day-offline job monitor must do one scan since Oct 4, not 3 blind replays. Blind replay is explicitly Rejected.

## Decision
Catch-up is semantic: each recurring/monitor task stores checkpoint + dedup keys + idempotent handlers. On recovery, scheduler computes one covering run from checkpoint to now; workers dedup notifications and side effects.

## Alternatives considered + why rejected
- Blind missed-schedule replay: rejected — spam (3× job alerts), wasted 1Mbps/compute, wrong on power-cut reality.
- Skip-all-missed (jump to now): rejected — loses real events (jobs, bills) during outage.
- Manual user triage of backlog: rejected — breaks autonomous-core promise; unusable after long outage.

## Consequences
- Requires checkpoint columns, dedup keys, and idempotent notify/store from Phase 5 onward.
- One covering run keeps LLM + bandwidth cost near-constant regardless of outage length.
- Phase 0 must do differently: include checkpoint/retry/attempt fields in Task schema now so Phase 5 needs no migration of basics.
